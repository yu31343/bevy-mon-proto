# 一、 项目核心开发内容 (MVP 阶段)

核心开发围绕“数据-逻辑-表现”三个维度展开，确保游戏闭环的完整性。

## 1. 核心架构与数据驱动
* **ECS 实体组件系统：** 将精灵（Entity）拆解为基础属性（Health, Attack, Speed）、技能列表（SkillList）和视觉状态（SpriteBundle）等独立组件。
* **数据解耦：** 建立基于配置（如 TOML/JSON）的精灵原型库，实现“数据定义属性，代码驱动逻辑”的解耦模式。

## 2. 回合制战斗逻辑状态机
* **行动流控：** 基于 Bevy `States` 实现战斗周期的严格管理：
    * **判定阶段：** 依据 `Speed` 属性计算行动顺序切片。
    * **指令阶段：** 等待玩家输入或 AI 决策。
    * **结算阶段：** 计算属性变化、触发技能特效、判定胜负。
* **伤害演算：** 实现标准的减法或乘法伤害公式，支持防御减伤与属性克制。

## 3. UI 交互与视觉呈现
* **动态 UI 系统：** 实时同步实体属性至 UI 界面（如血条 `ProgressBar`、技能菜单）。
* **战斗表现：** 利用 `bevy_tweening` 实现精灵的攻击平移、受击震动及数值漂浮文字。

## 4. 基础 AI 行为
* **决策模型：** 实现基于权重或简单规则的 AI（如：生命值低于 20% 优先回血，否则执行最高伤害攻击）。

# 三、 项目特色与创新点

本项目不仅是简单的复刻，更在技术栈应用与设计理念上具备独特性：

## 1. 技术栈的前沿性与高性能
* **内存安全保证：** 利用 Rust 的所有权机制，从底层根除空指针及资源竞态问题，确保战斗系统在高并发（如大规模 AI 运算）下的稳定性。
* **数据驱动的 ECS 范式：** 相比传统 OOP 游戏开发，本项目采用 Bevy 的 ECS 架构。这种**“组合优于继承”**的设计使得精灵的功能扩展极其灵活——只需为实体挂载一个新的 `Component`，即可为其增加全新的战斗机制（如“反击”或“光环”）。

## 2. 极致的模块化设计
* **插件化架构：** 将战斗、AI、UI 各自封装为 Bevy `Plugin`。这意味着战斗逻辑可以无缝迁移到不同的场景（如从 2D 切换到 3D），或者方便地进行单元测试。

## 3. 策略深度的潜力
* **基于“速度流”的动态回合：** 不同于固定的你一刀我一刀，系统支持基于速度属性的动态排序，为后续引入“拉条”、“控制速度”等高级策略打下基础。

## 4. 开发者友好型工具链
* **热重载支持：** 结合 Rust 的编译特性与 Bevy 的资源管理，项目可实现不重启程序即可修改精灵数值或技能效果，极大提升了策划调优的效率。

目前元素的附着和反应等战斗逻辑设计得比较直接但具备一定的深度。这里为您详细拆解一下这部分机制的技术实现和设计规则：

### 1. 元素基础和克制关系 (`ElementMatrix`)
所有的元素类型枚举 (`ElementType`) 有 7 种：火、水、草、光、暗、雷、风。
元素的克制机制由 `ElementDb` 通过哈希表进行配置驱动（从 `assets/data/battle_data.ron` 中读取）。
*   **克制关系（例如 水克火）：** 克制方的倍率为 `2.0`。
*   **微弱关系（例如 火打水）：** 被克制方的攻击倍率为 `0.5`。
*   **无特定关系：** 默认倍率为 `1.0`。

### 2. 元素附着 (`ElementAura` 组件)
战斗中的每一个精灵（`Combatant`）身上都会挂载一个 `ElementAura` 组件，这个组件用来记录当前实体**实时生效的元素附着（Buff/Debuff）**。
*   **初始附着：** 在 `init_battle_system` 中，部分天生自带元素的精灵（目前代码里特殊设定了 **火、光、暗** 这三系）在出生时会默认把自己的本系元素作为初始的 `ElementAura` 附着在身上，而其他的精灵出生时附着为 `None`。
*   **附着条件：** 只要使用的是带有**元素属性**的攻击技能，在造成**未被护盾完全抵挡**的伤害后，技能附带的元素就会**直接替换**掉目标身上原有的元素附着。

### 3. 元素反应与伤害结算逻辑 (`apply_effect` 函数)
当一方使用 `Attack` 技能攻击另一方时，结算的流程非常清晰，特别是引入了“护盾免疫”机制。这里的反应更多体现为**“覆盖”**和**“实时克制计算”**。

具体的伤害计算和元素反应流程如下：

1.  **计算基础伤害（Raw Damage）：**
    `基础伤害 = 技能威力 + 待命增益(来自卡牌) + 攻击方攻击力 - 防御方防御力`
2.  **判断技能是否有元素：**
    *   **无元素（物理攻击）：**
        直接用基础伤害去扣除护盾（若有），剩余的扣除生命值。不发生任何元素附着。
    *   **有元素（元素攻击）：**
        *   **第一步计算：尝试利用目标身上的 `ElementAura`（元素附着）进行克制计算。**
            它会取目标当前的 `ElementAura`（如果附着为空 `None`，则降级取精灵本身的固有元素 `target_element`），然后从矩阵中获取倍率，计算出**理论伤害（带附着版）**。
        *   **第二步：护盾免疫判定（核心机制）。**
            系统会看目标身上的**护盾**能否抵挡住这个“理论伤害”中的一部分（即 `absorbed_with_aura > 0`）：
            *   **情况 A（护盾生效了，吸收了部分或全部伤害）：**
                这就是**“盾免疫元素附着/反应”**的机制。如果护盾被触发了，之前的带附着倍率作废。系统会改用**防守方精灵的固有元素**（不再考虑他身上挂着什么元素）重新计算一遍没有附着的克制倍率和伤害。**此时不发生元素附着改变（不会刷新目标的 Aura）。**
            *   **情况 B（护盾没有吸收任何伤害，比如破盾了或者本来就没盾）：**
                目标的护盾没有抵挡伤害，那么系统判定攻击“打实”了。
                这个时候，直接使用**第一步带有附着倍率的理论伤害**来扣血。
                并且发生“反应”（覆盖）：目标身上的 `ElementAura` 会**立刻变成攻击方技能的元素**。
                系统会发送一个 `ElementAuraApplied` 事件，记录从什么元素变成了什么元素。

### 总结
*   **目前没有复杂的多元素混合反应（例如水+火=蒸发）**，它的反应机制其实是**“元素覆盖”和“动态属性弱点”**。你给敌人打上什么元素，敌人当前的“弱点属性”就会临时变成这个元素，下一次攻击就会按照这个新元素来计算克制（除非对方有盾）。
*   **护盾是绝对的元素防御：** 只要有护盾参与了伤害吸收，就不允许挂元素，也不允许触发对方身上已有附着的弱点判定，强制回归判定精灵的本体属性。这使得套盾成为了应对元素克制的一大核心策略。
